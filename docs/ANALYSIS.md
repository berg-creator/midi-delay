# MIDI-Driven Pitch Delay — технический разбор

> Документ для людей и для будущих сессий агента. Читается первым, чтобы не переизобретать решённые вопросы.

## 1. Что мы строим

Аудио-эффект (VST3 / AU), который принимает **аудио + MIDI**. Аудио пишется в кольцевой буфер.
Приходящая MIDI-нота порождает **голос**: он читает буфер с задержкой `delayTime`, воспроизводит его
с транспонированием под ноту, с огибающей из `velocity`, длиной по длительности ноты.

Это **не** классический feedback-дилей с питчем. Это **полифонический MIDI-триггерируемый
tap-delay поверх общего буфера записи**. Разница принципиальная — см. §3.

Целевое применение: тихий фоновый подклад (вокал/инструмент), дублирующий мелодию припева.
Это важно: цель — «еле заметный слой в миксе», а не solo-качество харморайзера. Планка качества
питчинга ниже, чем у Melodyne/Harmony, и это сильно упрощает MVP.

## 2. Оценка сложности

**Средняя. Не research-проект.** Все компоненты — решённые задачи с известной литературой.
Риск сосредоточен не в DSP, а в UX и интеграции с FL Studio.

| Блок | Сложность | Оценка (вечерами) |
|---|---|---|
| Скелет плагина, CMake/JUCE, CI | низкая | 3–5 дней |
| Кольцевой буфер + дробное чтение | низкая | 2 дня |
| MIDI-приём, sample-accurate тайминг | низкая-средняя | 2–3 дня |
| Voice manager, полифония, огибающие | средняя | 5–7 дней |

**MVP: ~1.5–2.5 месяца неполной занятости** при уверенном C++.
Без опыта C++/DSP — умножить на 2–3, и начинать с M0–M1, не заглядывая дальше.

## 3. Ключевая архитектурная развилка (решить до первой строки DSP)

**A. Voice-based tap delay (рекомендуется).**
Один общий кольцевой буфер записи. MIDI-нота → голос со своими: позицией чтения, ratio,
огибающей, паном. Полифония бесплатно (аккорды работают), длительность ноты управляет длиной
хвоста, velocity — громкостью. Это ровно то, что описано в концепции.

**B. Feedback delay line с питчем в петле.**
Классический дилей, весь хвост питчится. Проще, но: аккорды невозможны, длительность ноты
некуда деть, а питч в петле обратной связи кумулятивно уползает (эффект Шепарда).

→ **Берём A.** B оставить нельзя даже как опцию MVP — это другой плагин.

## 4. Как считается сдвиг питча: два режима

**Relative / Root Key (MVP).**
Пользователь задаёт опорную ноту (Root). `semitones = midiNote − rootNote`,
`ratio = 2^(semitones/12)`. Никакого pitch detection, ноль латентности, полная предсказуемость.
Покрывает 90% сценария «подклад по мелодии припева».

**Absolute / Harmonizer (post-MVP).**
Детектим F0 входа (YIN / pYIN), `ratio = f_target / f_source`. Настоящий харморайзер: MIDI задаёт
абсолютную высоту независимо от того, что поёт вокалист. Дороже: pitch tracker, look-ahead,
деградация на неголосовом и на шёпоте/консонантах.

→ MVP — только Relative. Absolute — v1.1, отдельной веткой.

## 5. Алгоритм pitch shift

| Вариант | Качество | Латентность | Стоимость реализации |
|---|---|---|---|
| **Dual-head varispeed + crossfade** | средн. (норм до ±7 пт) | 0 (алгоритмическая ~окно) | ~150 строк |
| PSOLA | хорошее для вокала | требует pitch marks | высокая |
| Phase vocoder (Laroche–Dolson) | хорошее, полифония | окно 2048 ≈ 43 мс @48k | высокая |
| Signalsmith Stretch (header-only) | хорошее | настраиваемая | низкая, но проверить лицензию |
| Rubber Band | отличное | средняя | низкая, лицензия GPL/коммерческая |

→ **MVP: свой dual-head varispeed.** Два ридера, смещённых на пол-окна, кроссфейд по
**equal-power** (не линейный). Окно ~50–80 мс для голоса. Полный контроль, ноль зависимостей,
артефакты приемлемы для тихого фонового слоя.
→ **HQ-режим позже:** подключить Signalsmith или Rubber Band как второй движок за флагом
`Quality: Fast / HQ`. Перед подключением — **проверить лицензию** (Rubber Band требует покупки
для закрытого коммерческого продукта).

### Главный инсайт: дилей прячет латентность питчера
Любой качественный питч-алгоритм требует буфера/look-ahead. Обычный харморайзер платит за это
репортируемой латентностью. **У нас — нет:** алгоритмический буфер вычитается из `delayTime`.
Пока `delayTime ≥ algorithmLatency`, плагин репортит **нулевую задержку**.
Практическое правило: `readOffset = delayTime − algLatency`, минимальный `delayTime` = `algLatency`.
Это снимает главное ограничение на выбор алгоритма и открывает дорогу к HQ-движку без боли PDC.

## 6. Узкие места и решения

1. **Джиттер MIDI внутри блока.** `juce::MidiBuffer` даёт sample offset у каждого события —
   его надо уважать, а не запускать все ноты в начале блока. Иначе дрожание до размера буфера
   (≈10 мс на 512 сэмплах). Обрабатывать блок сегментами между MIDI-событиями.
2. **MIDI-роутинг в FL Studio.** Исторически болезненный (MIDI Out → порт → плагин), компенсация
   задержки работает не так, как в Live/Logic. Обязателен параметр **MIDI Offset (±ms)** — ручной
   калибровочный винт. Реальный мир всегда дрейфует, минимальная модель этого не увидит.
3. **Кумулятивный питч-дрейф.** Feedback брать **до** питч-стадии (чистый сигнал). Иначе каждый
   круг транспонирует хвост заново и подклад уползает вверх/вниз.
4. **«Бурундук»/форманты** на сдвигах > ±7 полутонов. MVP: ограничить диапазон и мягкая атака.
   Formant preservation — post-MVP. Для тихого слоя лёгкая нечеловечность даже работает на образ.
5. **Транзиенты и клики.** Атака огибающей 5–20 мс, fade-out при voice stealing, equal-power
   кроссфейды. Большинство артефактов гасится огибающей, а не алгоритмом.
6. **Полифония и CPU.** Лимит 8–16 голосов, voice stealing по возрасту/громкости.
   Стоимость линейна по голосам — профилировать рано, цель в §7.
7. **Realtime safety.** В `processBlock`: никаких аллокаций, локов, логов, исключений.
   `ScopedNoDenormals`, атомарные параметры, `SmoothedValue` на всё, что слышно.
8. **Sync с темпом.** `AudioPlayHead::PositionInfo` → BPM. Нотные длительности + dotted/triplet,
   плюс free-режим в мс. Смена delay time на ходу — либо с кроссфейдом, либо только на границе ноты.

## 7. Целевые показатели MVP

- Репортируемая латентность: **0 сэмплов** при `delayTime ≥ algLatency`.
- CPU: **< 5%** одного ядра M1 при 8 голосах, 48 кГц, буфер 128.
- pluginval strictness **10** — зелёный, VST3 и AU.
- Тайминг: старт хвоста в пределах **±1 мс** от MIDI-события (после калибровки Offset).

## 8. Стек

- **C++20 + JUCE 8**, сборка через **CMake** (JUCE как submodule или FetchContent).
- Форматы: **VST3** (приоритет — FL Studio), **AU** (macOS), **Standalone** (для отладки без DAW).
- Флаг `JucePlugin_WantsMidiInput=1` обязателен: без него FL не покажет MIDI-вход.
- Тесты: офлайн-рендер (файл → файл) + сравнение с эталоном. Без фреймворков, пока не жмёт.
- **pluginval** (Tracktion) в CI на каждый PR.
- CI: GitHub Actions, matrix macOS (universal arm64+x86_64) / Windows x64.
- Подпись/нотаризация macOS — отдельная задача перед релизом. **На этой машине стоит только
  Command Line Tools, полного Xcode нет** — для AU-таргета и нотаризации это придётся решить.

## 9. Стратегическая заметка: внутренний секвенсер

Барьер входа №1 для пользователя — не качество питчинга, а **как вообще подать MIDI в эффект
в FL Studio**. Многие бросят на этом шаге. Сильная альтернатива: встроенный мини-пиано-ролл
внутри плагина — мелодия рисуется прямо в UI, MIDI-роутинг не нужен вовсе.
Так делают Waves Harmony и Auto-Tune Harmony — не случайно.
Для MVP оставляем MIDI-вход (это заявленная киллер-фича), но внутренний паттерн — первый
кандидат в v1.1, и, возможно, именно он продаст плагин.
